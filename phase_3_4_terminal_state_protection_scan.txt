SECTION 7 - PHASE 3.4 CANONICAL DESIGN QUESTIONS
================================================================================

1. What exactly is a terminal workflow state?

Canonical authority:

    COMPLETED
    FAILED
    CANCELLED
    ABORTED

These come from the frozen Universal Workflow Contract and Phase 3.1.


2. Should Phase 3.4 define terminal states again?

NO.

3.4 must consume:

    is_terminal_workflow_state(...)
    terminal_workflow_states(...)

from frozen Phase 3.1.


3. Should Phase 3.4 define lifecycle transition edges?

NO.


4. Should Phase 3.4 decide whether a normal transition edge is legal?

NO.

That remains Phase 3.2.


5. What new authority does Phase 3.4 add?

Explicit protection semantics:

    Once a workflow has reached a terminal state,
    no lifecycle mutation may move it to any other state.


6. But Phase 3.2 already rejects outgoing terminal transitions.
Why do we still need 3.4?

Because:

3.2 answers:

    "Is this requested edge declared?"


3.4 answers:

    "Is mutation from this current workflow state prohibited because
     terminal state is lifecycle-final?"


This creates an explicit lifecycle immutability guard instead of relying
only on the absence of graph edges.


7. Should 3.4 allow COMPLETED -> COMPLETED?

NO mutation.

A request that leaves status unchanged should not be treated as a
lifecycle transition.

Phase 3.2 already rejects self-edges.


8. Should 3.4 allow FAILED -> RECOVERING?

NO.

FAILED is terminal.

Recovery after terminal failure is NOT modeled as mutation of the same
terminal workflow back into RECOVERING.

Any future recovery strategy belongs to Phase 9.


9. Should 3.4 allow CANCELLED -> READY?

NO.


10. Should 3.4 allow ABORTED -> RUNNING?

NO.


11. Does 3.4 protect only COMPLETED?

NO.

All four canonical terminal states are protected equally.


12. Should a non-terminal state be considered protected?

NO.

CREATED
READY
RUNNING
WAITING
PAUSED
RECOVERING

are not terminal-protected.


13. Should 3.4 mutate a workflow object itself?

NO.

It supplies a guard/protection decision that a future lifecycle mutation
operation must require before mutating state.


14. Should 3.4 return only bool?

Preferred:
NO.

Use immutable protection evidence.


15. Proposed protection result:

    TerminalStateProtectionResult


Potential fields:

    current_state
    requested_state
    current_state_is_terminal
    mutation_prohibited
    protection_reason
    protection_version


16. Should requested_state be mandatory?

For transition-specific protection:
YES.

Potential APIs may include both:

    inspect_terminal_state_protection(current_state)

and:

    validate_terminal_state_mutation(
        current_state,
        requested_state
    )


17. Should inspection of a terminal state require requested_state?

NO.

Example:

    inspect_terminal_state_protection("FAILED")

should be able to say:

    terminal = True
    protected = True


18. Should inspection of RUNNING say protected?

NO.


19. Should invalid current state return evidence or raise?

Recommended:

    inspect_terminal_state_protection(...)
        returns invalid protection result/evidence

while:

    require_terminal_state_mutation_allowed(...)
        raises on invalid input or protected mutation


20. Should mutation guard use Phase 3.2?

YES for non-terminal requested transitions.

Flow:

    normalize current/requested
        ↓
    if current terminal
        → prohibit mutation immediately
    else
        ↓
    delegate requested edge legality to Phase 3.2


21. Does this make 3.4 a second validator?

NO.

3.4 does not define edge legality.

It composes:

    terminal protection decision
    +
    frozen 3.2 transition validation


22. Should a non-terminal invalid edge be described as terminal-protected?

NO.

Example:

    WAITING -> COMPLETED

Phase 3.4 result:

    current_terminal = False
    terminal_protection_triggered = False
    transition_valid = False

Reason:

    transition rejected by Phase 3.2

This preserves authority separation.


23. Should a terminal outgoing request call 3.2 first?

Recommended:
NO.

Terminal protection can short-circuit immediately because the lifecycle
immutability rule is stronger and explicit.

However, 3.4 may include 3.2 provenance in its result.


24. Should terminal protection have a canonical violation/protection code?

YES.

Proposed:

    terminal_state_mutation_prohibited


25. Should invalid current state use another code?

YES.

    current_state_invalid


26. Should invalid requested state use another code?

YES.

    requested_state_invalid


27. Should non-terminal invalid edge reuse Phase 3.2 evidence?

YES.

Do not invent new edge-legality vocabulary.

Potential reason:

    transition_not_declared


28. Should 3.4 record history?

NO.


29. Should 3.4 persist protection decisions?

NO.


30. Should 3.4 generate timestamps?

NO.


31. Should 3.4 know workflow IDs?

Not required for the pure state-level guard.

Future mutation integration can carry workflow identity externally.


32. Should 3.4 import Runtime?

NO.


33. Should 3.4 import registries?

NO.


34. Should 3.4 know stage results?

NO.


35. Should 3.4 know recovery policy?

NO.


36. Should 3.4 decide what new workflow to create after terminal failure?

NO.

That is Phase 9 recovery policy.

SECTION 11 - TERMINAL PROTECTION MATRIX
================================================================================

Terminal states:

    COMPLETED
    FAILED
    CANCELLED
    ABORTED


Every mutation request from each terminal state must be rejected:

    COMPLETED -> any state
    FAILED -> any state
    CANCELLED -> any state
    ABORTED -> any state


This includes self-target requests:

    COMPLETED -> COMPLETED
    FAILED -> FAILED
    CANCELLED -> CANCELLED
    ABORTED -> ABORTED


Reason:

A lifecycle mutation request from terminal state is prohibited.

This is stronger/more explicit than merely saying no graph edge exists.

        ↓
    mutation
        ↓
    3.3 history entry

But Phase 3.4 itself owns ONLY the protection guard.
