14. Should FAILED automatically imply recovery?

Expected:
NO.

FAILED is currently terminal in the frozen Phase 1.1 contract.

Recovery policy belongs to Phase 9.

Therefore do not silently redefine FAILED as non-terminal.


15. What is RECOVERING for if FAILED is terminal?

Expected architectural distinction:

    RECOVERING is a non-terminal operational lifecycle state entered
    before a terminal FAILED outcome where recovery handling is active.

It should not mean "leave FAILED and become RECOVERING" unless a future
canonical contract explicitly changes terminal semantics.


16. Should WAITING be distinct from PAUSED?

Expected:
YES.

WAITING:
    workflow cannot currently advance because it is awaiting a dependency,
    external completion, branch/join condition, or required coordination event.

PAUSED:
    workflow has been deliberately suspended.

The exact event semantics may be refined in later phases.


17. Should READY be distinct from CREATED?

Expected:
YES.

CREATED:
    workflow instance exists.

READY:
    workflow has passed prerequisites needed to begin execution.


18. Should RUNNING be the only state from which stage execution occurs?

Architecture expectation:
Generally YES, but Phase 3.1 does not execute anything.

Phase 3.1 only expresses lifecycle state semantics.


19. Should CANCELLED and ABORTED remain distinct?

Expected:
YES.

CANCELLED:
    controlled cancellation.

ABORTED:
    workflow termination outside normal controlled completion/cancellation
    progression.

Do not collapse them.


20. Should Version Management or Registration modify lifecycle state?

Expected:
NO.

Phase 2 remains frozen and separate.
